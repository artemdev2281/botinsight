# Модель данных BotInsight

Реализованы подключение backend к PostgreSQL, классы `Project`, `Scenario`, `Dialog`, `Message` и `BacklogItem`, их связи и команда создания всех пяти таблиц. Для всех пяти сущностей реализованы схемы валидации и CRUD API. Время сообщения проверяется при его записи и при изменении временных границ диалога.

## Границы

Основные сущности: проект, сценарий, диалог, сообщение и задача backlog. Для каждой реализованы создание, чтение, изменение и удаление через API.

Пользователь приложения — аналитик или участник команды, работающий в BotInsight. Собеседник чат-бота — внешний пользователь, чьи сообщения попали в логи. Это разные роли.

Таблицу пользователей BotInsight, связь владельца с проектом и вход в приложение добавляем в лабораторной №4. Во второй лабораторной доступ к API ещё не разграничивается по владельцам.

Импорт файлов и расчёт аналитики по загруженным логам относятся к последующему развитию продукта. Сейчас проектируем данные, на которых они будут работать.

## Связи

| Родительская запись | Связанные записи | Как хранится связь |
|---|---|---|
| Проект | Много сценариев | `scenarios.project_id` |
| Проект | Много диалогов | `dialogs.project_id` |
| Проект | Много задач backlog | `backlog_items.project_id` |
| Сценарий | Много диалогов | `dialogs.scenario_id`, связь необязательна |
| Диалог | Много сообщений | `messages.dialog_id` |

В первой версии один диалог относится максимум к одному сценарию. Диалог без определённого сценария также допустим. Проект сообщения определяется через его диалог, поэтому отдельное поле `project_id` в сообщении не требуется.

## 1. Проект — projects

Один анализируемый чат-бот. Например, Support Bot.

| Поле | Тип данных | Назначение и правила |
|---|---|---|
| `id` | Целое число | Первичный ключ, назначается автоматически |
| `name` | Строка до 100 символов | Обязательное непустое название |
| `description` | Текст | Описание, по умолчанию пустая строка |
| `created_at` | Дата и время с часовым поясом | Время создания записи, назначается автоматически |

Количество диалогов не хранится отдельным полем: оно вычисляется по связанным диалогам.

API проектов поддерживает создание, список, просмотр, полное обновление названия и описания через `PUT` и удаление с каскадным удалением связанных записей. Схемы `ProjectCreate` и `ProjectUpdate` проверяют тело запроса, а `ProjectRead` задаёт поля ответа. Название обязательно; пропущенное описание принимается как пустая строка. В частности, при `PUT` пропуск описания очищает ранее сохранённый текст. Идентификатор и дата создания доступны только в ответах. Маршруты и статусы описаны в README.

## 2. Сценарий — scenarios

Пользовательская задача, которую помогает выполнить бот. Например, «Перевод денег».

| Поле | Тип данных | Назначение и правила |
|---|---|---|
| `id` | Целое число | Первичный ключ |
| `project_id` | Целое число | Обязательный внешний ключ на проект |
| `name` | Строка до 150 символов | Обязательное непустое название, уникальное в пределах проекта |
| `description` | Текст | Описание, по умолчанию пустая строка |

Одинаковые названия сценариев в разных проектах допустимы.

CRUD сценариев реализован по адресам `/projects/{project_id}/scenarios` и `/projects/{project_id}/scenarios/{scenario_id}`. Проект берётся из адреса, его изменение через тело запроса запрещено. Запрос конкретного сценария учитывает одновременно его `id` и `project_id`. Сценарий другого проекта возвращает `404`. Повтор названия в одном проекте возвращает `409`. Полное обновление через `PUT` требует название и заменяет пропущенное описание пустой строкой. Удаление сценария сохраняет его диалоги и сообщения.

## 3. Диалог — dialogs

Одна беседа пользователя с чат-ботом. Объединяет сообщения и хранит итог беседы.

| Поле | Тип данных | Назначение и правила |
|---|---|---|
| `id` | Целое число | Первичный ключ |
| `project_id` | Целое число | Обязательный внешний ключ на проект |
| `scenario_id` | Целое число или пустое значение | Необязательный внешний ключ на сценарий того же проекта |
| `external_id` | Строка до 255 символов или пустое значение | Номер диалога в исходных логах; при наличии уникален в пределах проекта |
| `started_at` | Дата и время с часовым поясом | Обязательное время начала беседы |
| `ended_at` | Дата и время с часовым поясом или пустое значение | Время завершения, не раньше начала |
| `status` | Строка из заданного списка | Обязательный итог диалога |

Для первой версии анализируем завершённые беседы. Возможные итоги:

- `completed` — задача пользователя выполнена;
- `abandoned` — пользователь прервал беседу;
- `fallback` — беседа завершилась из-за непонятого запроса;
- `operator` — беседу передали оператору.

У диалога один итог. Непонятое сообщение внутри беседы не обязательно означает итог `fallback`: пользователь мог переформулировать вопрос и завершить сценарий успешно. Если время завершения неизвестно из логов, `ended_at` можно не указывать.

Принадлежность сценария проекту защищена составным внешним ключом пары `scenario_id` и `project_id` на пару `id` и `project_id` таблицы `scenarios`. Для этой ссылки в `scenarios` добавлено ограничение уникальности пары `id` и `project_id`. При удалении сценария действие `SET NULL (scenario_id)` очищает только ссылку на сценарий. Проект диалога сохраняется. Для существующей базы изменение таблицы `scenarios` сохранено в `backend/migrations/001_scenarios_project_key.sql`; порядок применения описан в README.

CRUD диалогов реализован по адресам `/projects/{project_id}/dialogs` и `/projects/{project_id}/dialogs/{dialog_id}`. Проект берётся из адреса и не меняется через тело запроса. `DialogCreate` и `DialogUpdate` требуют начало с часовым поясом и допустимый итог; необязательные поля по умолчанию равны `null`. При полном обновлении через `PUT` пропуск необязательного поля очищает его. Бизнес-логика проверяет сценарий и сохраняет временные границы уже существующих сообщений. Нарушение бизнес-правила возвращает `422`, повтор `external_id` — `409`, запрос диалога другого проекта — `404`. Удаление диалога удаляет его сообщения.

## 4. Сообщение — messages

Одна реплика пользователя, бота или оператора внутри диалога.

| Поле | Тип данных | Назначение и правила |
|---|---|---|
| `id` | Целое число | Первичный ключ |
| `dialog_id` | Целое число | Обязательный внешний ключ на диалог |
| `position` | Целое число от 1 | Порядковый номер реплики, уникальный в пределах диалога |
| `role` | Строка из заданного списка | `user`, `bot` или `operator` |
| `text` | Текст | Обязательная непустая реплика |
| `sent_at` | Дата и время с часовым поясом | Обязательное время отправки |
| `intent` | Строка до 150 символов или пустое значение | Определённая ботом тема пользовательского запроса, например `money_transfer` |
| `confidence` | Дробное число от 0 до 1 или пустое значение | Оценка уверенности бота в определённой теме |
| `is_fallback` | Логическое значение | Был ли пользовательский запрос не обработан; по умолчанию `false` |

Для реплик бота и оператора `intent` и `confidence` пустые, `is_fallback` равен `false`. У пользовательской реплики тема и уверенность тоже могут отсутствовать, если исходные логи их не содержат.

Порядок реплик определяется по `position`, даже если время отправки совпадает. Время сообщения должно попадать в интервал диалога; при неизвестном времени завершения проверяется только нижняя граница.

Модель `Message`, ограничения её полей и CRUD API реализованы. Маршруты находятся внутри `/projects/{project_id}/dialogs/{dialog_id}/messages`. Запрос конкретного сообщения проверяет его принадлежность диалогу, а диалога — проекту. При загрузке списка записи упорядочиваются по `position`. Сообщения удаляются вместе с диалогом или при удалении из его ORM-коллекции.

Схемы `MessageCreate` и `MessageUpdate` требуют положительный целочисленный номер, допустимого автора, непустой текст и время с часовым поясом. Дополнительные поля распознавания разрешены только для `user`. `PUT` заменяет все редактируемые поля: пропущенные `intent` и `confidence` очищаются, а `is_fallback` становится `false`. Время сообщения проверяется относительно границ диалога; равенство допустимо. При записи сообщений диалог блокируется до завершения транзакции, как и при изменении его дат. Это сохраняет временную согласованность при одновременных запросах. Конфликт номера сообщения возвращает `409`, нарушение временных границ — `422`. Подробные форматы и ошибки описаны в README.

## 5. Задача на улучшение — backlog_items

Найденная проблема или запланированное улучшение чат-бота.

| Поле | Тип данных | Назначение и правила |
|---|---|---|
| `id` | Целое число | Первичный ключ |
| `project_id` | Целое число | Обязательный внешний ключ на проект |
| `title` | Строка до 200 символов | Обязательный непустой заголовок |
| `description` | Текст | Подробности, по умолчанию пустая строка |
| `priority` | Строка из заданного списка | `low`, `medium`, `high`; по умолчанию `medium` |
| `status` | Строка из заданного списка | `open`, `in_progress`, `done`; по умолчанию `open` |
| `source` | Строка из заданного списка | `requests`, `fallbacks`, `scenarios`, `manual`; по умолчанию `manual` |
| `created_at` | Дата и время с часовым поясом | Время создания записи, назначается автоматически |

Источник обозначает раздел, в котором нашли проблему. Ссылки на конкретное сообщение или сценарий в первой версии не храним. В интерфейсе технические значения отображаются русскими названиями: например, `high` — «Высокий», `open` — «Открыта».

Модель `BacklogItem` реализована. Задачи доступны через ORM-коллекцию `project.backlog_items`, проект задачи — через `backlog_item.project`. Удаление проекта или удаление задачи из его коллекции удаляет задачу. Удаление отдельной задачи сохраняет проект. Одинаковые заголовки задач допустимы.

CRUD задач реализован по адресам `/projects/{project_id}/backlog` и `/projects/{project_id}/backlog/{item_id}`. Схемы `BacklogItemCreate` и `BacklogItemUpdate` требуют заголовок и проверяют допустимые значения приоритета, статуса и источника. `PUT` заменяет все редактируемые поля: пропущенные поля получают значения по умолчанию. `BacklogItemRead` добавляет идентификатор задачи, идентификатор проекта и время создания. Проект берётся из адреса; задачу другого проекта нельзя просмотреть, изменить или удалить по этому адресу — возвращается `404`. Ошибки в полях возвращают `422`. Подробности описаны в README.

## Целостность данных и удаление

- Нельзя создать запись со ссылкой на несуществующий проект, сценарий или диалог.
- Сценарий диалога должен принадлежать тому же проекту, что и диалог. Смена связей также должна сохранять это правило.
- При удалении проекта удаляются его задачи, сценарии, диалоги и сообщения этих диалогов.
- Для реализованной связи проекта и сценариев также действует правило: удаление сценария из ORM-коллекции `project.scenarios` удаляет его запись. Сценарий не может существовать без проекта.
- При удалении диалога удаляются его сообщения.
- При удалении сценария диалоги сохраняются, их `scenario_id` становится пустым. Это сохраняет историю бесед.
- При удалении сообщения или задачи другие записи сохраняются. Пропуски в номерах `position` после удаления допустимы.
- Пустые названия и реплики из одних пробелов не принимаются. Значения вне заданных списков и диапазонов отклоняются.
- Уникальность идентификаторов, внешние ключи и допустимые значения защищаются ограничениями БД. API дополнительно проверяет данные и выдаёт понятные ошибки. При изменении диалога проверяется согласованность уже существующих сообщений.

## Откуда берётся аналитика

Отдельные таблицы Dashboard, fallback-запросов и сводных показателей не нужны: это представления одних и тех же исходных данных.

| Показатель или раздел | Расчёт по данным |
|---|---|
| Количество диалогов | Число диалогов проекта за выбранный период по `started_at` |
| Обращения по intents | Число пользовательских сообщений каждой темы и среднее известное `confidence` |
| Fallback-запросы | Пользовательские сообщения с `is_fallback = true` |
| Fallback rate | Доля fallback-запросов среди всех пользовательских сообщений |
| Completion rate | Доля диалогов с итогом `completed` среди всех диалогов выбранной группы |
| Abandoned rate | Доля диалогов с итогом `abandoned` среди всех диалогов выбранной группы |
| Operator rate | Доля диалогов с итогом `operator` среди всех диалогов выбранной группы |
| Fallback в таблице сценариев | Доля диалогов с итогом `fallback` среди диалогов конкретного сценария |

Период для сообщений определяется по `sent_at`, для диалогов — по `started_at`. Диалоги без сценария участвуют в общей аналитике проекта, но не в статистике конкретного сценария. Неизвестный intent отображается отдельной группой, отсутствующие значения confidence не входят в среднее. Если подходящих записей нет, интерфейс показывает отсутствие данных.

Fallback rate по сообщениям и доля диалогов с итогом fallback — разные показатели. В текущем демонстрационном frontend число fallback-запросов приблизительно выводится из числа диалогов и процента. При интеграции его потребуется заменить реальным количеством соответствующих сообщений.

## Пример

В проекте Support Bot есть сценарий «Перевод денег». Диалог №42 связан с этим проектом и сценарием. В нём пользователь написал «Как отменить перевод?», а бот не распознал запрос: у пользовательского сообщения `is_fallback = true`. Если беседу передали оператору, итог диалога — `operator`.

Аналитик создаёт в этом же проекте задачу «Добавить отмену перевода» с источником `fallbacks`. Так модель поддерживает путь от исходной беседы до задачи на улучшение.
