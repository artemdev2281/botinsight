# BotInsight

Платформа развития чат-ботов на основе анализа диалогов

# Суть продукта

**BotInsight** - платформа для анализа данных о взаимодействии пользователей с чат-ботами. Система позволяет загружать логи диалогов, исследовать структуру пользовательских обращений, находить необработанные запросы и проблемные сценарии, отслеживать ключевые показатели работы чат-бота и формировать backlog улучшений.

Основная задача продукта - преобразовать данные о взаимодействиях пользователей с чат-ботом в понятную продуктовую аналитику

## Назначение

Команды, развивающие чат-ботов, накапливают большое количество данных о диалогах. Из сырых данных можно извлекать информацию для принятия продуктовых решений. Для этого данные необходимо структурировать, обрабатывать и интерпретировать.

BotInsight позволяет:

- изучать обращения пользователей к чат-боту;
- находить запросы, которые бот не смог корректно обработать;
- выявлять проблемные сценарии и этапы диалога;
- отслеживать основные показатели работы чат-бота;
- фиксировать найденные проблемы в backlog улучшений.

## Пользовательские сценарии

### Основные сценарии

- Создание проекта для анализируемого чат-бота.
- Загрузка логов диалогов в формате CSV или JSON.
- Просмотр основных показателей проекта.
- Исследование структуры и динамики пользовательских обращений.
- Анализ fallback-запросов.
- Оценка успешности пользовательских сценариев.
- Поиск проблемных этапов диалога.
- Создание задач на улучшение продукта.
- Управление backlog'ом.

### Примеры сквозных сценариев

**Поиск причин fallback:** 
Изучение Dashboard → Обнаружение высокого fallback rate → Переход в раздел fallback-запросов → Изучение проблемных сообщений → Создание задачи в backlog.

**Поиск проблемного сценария:** 
Изучение Dashboard → Обнаружение снижения completion rate → Переход в раздел сценариев → Поиск проблемного этапа → Изучение диалогов → Создание задачи на изменение сценария.

**Анализ изменений в обращениях:** 
Изучение обращений → Обнаружение роста определённого intent'а → Анализ сообщений → Оценка необходимости улучшения → Создание задачи в backlog.

## Функциональные модули

### Проекты

Создание и управление анализируемыми чат-ботами. Один пользователь может иметь несколько независимых проектов.

### Импорт данных

Загрузка логов чат-бота в фиксированном формате CSV или JSON. 

### Dashboard

Сводное представление основных показателей проекта.

### Анализ обращений

Исследование пользовательских запросов:

- intents;
- количество и динамика обращений;
- confidence;
- fallback rate.

### Анализ fallback-запросов

Исследование сообщений, которые чат-бот не смог корректно обработать:

- fallback rate;
- динамика;
- исходные сообщения;
- intents и confidence;
- связанные сценарии.

### Анализ сценариев

Оценка прохождения пользовательских сценариев:

- completion rate;
- abandoned;
- fallback;
- перевод на оператора;
- проблемные этапы сценария.

### Backlog улучшений

Список задач на улучшение продукта.

Основные атрибуты:

- название;
- описание;
- приоритет;
- статус;
- источник проблемы.

Статусы: `Открыта`, `В работе`, `Выполнена`.

### Авторизация

Регистрация, вход в систему и доступ пользователя к своим проектам.

## Лабораторная работа №2 — backend

Подготовлено приложение на FastAPI и подключение PostgreSQL через SQLAlchemy. Проверочный маршрут `GET /` возвращает сообщение о работе API, а `GET /health/db` проверяет соединение с БД. Реализованы все пять моделей, их связи, команда создания таблиц и CRUD проектов, сценариев, диалогов, сообщений и задач backlog через API со схемами валидации запросов и ответов. Проверяются время сообщений и изменение временных границ диалогов. Итоговая техническая проверка выполнена; [результаты и порядок ручной проверки](docs/lab2-check.md). Фиксация изменений в Git пока отложена по просьбе автора проекта.

### Установка и запуск в Windows PowerShell

Нужен Python 3.12 или новее. Из корневой папки проекта выполните:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Копировать `.env.example` нужно только при первой настройке, если `.env` ещё не создан. В `.env` укажите параметры своего PostgreSQL:

```dotenv
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=botinsight
DB_USER=postgres
DB_PASSWORD=
```

После `DB_PASSWORD=` впишите пароль, заданный для пользователя `postgres` при установке PostgreSQL. Если пароль содержит `#` или пробелы, заключите значение в двойные кавычки. Не добавляйте `.env` в Git; `.env.example` должен оставаться без пароля. Переменные окружения процесса имеют приоритет над значениями из `.env`.

### Подготовка PostgreSQL

Сервер PostgreSQL должен быть запущен. Для локальной разработки используем пользователя `postgres`, созданного при установке. Создайте базу один раз, если её ещё нет:

```powershell
createdb -h 127.0.0.1 -p 5432 -U postgres -W botinsight
```

Команда запросит пароль. Если `createdb` не найден, для установленной версии PostgreSQL 18 используйте полный путь:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\createdb.exe" -h 127.0.0.1 -p 5432 -U postgres -W botinsight
```

### Создание таблиц

После создания базы и настройки `.env` выполните из папки `backend`:

```powershell
.\.venv\Scripts\python.exe init_db.py
```

Команда создаёт таблицы, описанные в `models.py`: `projects`, `scenarios`, `dialogs`, `messages` и `backlog_items`. Для новой пустой базы достаточно этой команды. Если база создана по более ранней версии проекта, сначала выполните подходящее обновление из раздела ниже.

Таблица `projects`:

| Поле | Назначение |
|---|---|
| `id` | Целочисленный первичный ключ, назначается автоматически |
| `name` | Обязательное название до 100 символов; пустая строка и строка из одних пробельных символов запрещены |
| `description` | Обязательный текст; при пропуске используется пустая строка |
| `created_at` | Дата и время с часовым поясом, назначаются базой автоматически |

Таблица `scenarios`:

| Поле | Назначение |
|---|---|
| `id` | Целочисленный первичный ключ, назначается автоматически |
| `project_id` | Обязательный внешний ключ на `projects.id` |
| `name` | Обязательное название до 150 символов; пустые и пробельные названия запрещены |
| `description` | Обязательный текст; при пропуске используется пустая строка |

Название сценария уникально в пределах проекта: пара `project_id` и `name` не может повторяться. В разных проектах одинаковые названия разрешены. Сценарий без существующего проекта создать нельзя.

В Python коллекция `project.scenarios` содержит сценарии проекта, а атрибут `scenario.project` даёт доступ к проекту сценария. При удалении проекта его сценарии удаляются каскадно. При удалении отдельного сценария проект сохраняется. Удаление сценария из коллекции `project.scenarios` также удаляет его запись, поскольку сценарий не может существовать без проекта.

Повторный запуск команды сохраняет существующие таблицы и записи. `create_all` создаёт отсутствующие таблицы, но не изменяет структуру уже существующих.

Таблица `dialogs`:

| Поле | Назначение |
|---|---|
| `id` | Целочисленный первичный ключ, назначается автоматически |
| `project_id` | Обязательный внешний ключ на проект |
| `scenario_id` | Необязательная ссылка на сценарий того же проекта |
| `external_id` | Идентификатор из исходных логов, до 255 символов; при наличии уникален внутри проекта |
| `started_at` | Обязательные дата и время начала с часовым поясом |
| `ended_at` | Необязательные дата и время завершения, не раньше начала |
| `status` | Обязательный итог: `completed`, `abandoned`, `fallback` или `operator` |

Проект диалога доступен через `dialog.project`, сценарий — через `dialog.scenario`. Обратные коллекции — `project.dialogs` и `scenario.dialogs`. Сценарий может отсутствовать, в том числе после его удаления: PostgreSQL очищает только `scenario_id`, сохраняя диалог и его проект. Удаление проекта удаляет его диалоги. Удаление диалога не удаляет проект или сценарий.

Составной внешний ключ проверяет пару `scenario_id` и `project_id`, поэтому сценарий другого проекта указать нельзя. Дополнительное ограничение уникальности пары `id` и `project_id` в `scenarios` позволяет ссылаться на эту пару. В ORM аргумент `foreign_keys` связи со сценарием указывает только `scenario_id`: назначение сценария не должно автоматически менять проект диалога. Используется PostgreSQL 15 или новее: действие `SET NULL (scenario_id)` очищает только указанную часть составного ключа.

Таблица `messages`:

| Поле | Назначение |
|---|---|
| `id` | Целочисленный первичный ключ, назначается автоматически |
| `dialog_id` | Обязательный внешний ключ на диалог |
| `position` | Порядковый номер от 1, уникальный в пределах диалога |
| `role` | Автор реплики: `user`, `bot` или `operator` |
| `text` | Обязательный текст, содержащий хотя бы один непробельный символ |
| `sent_at` | Обязательные дата и время отправки с часовым поясом |
| `intent` | Необязательная тема пользовательского запроса, до 150 символов |
| `confidence` | Необязательная оценка уверенности от 0 до 1 |
| `is_fallback` | Признак непонятого пользовательского запроса, по умолчанию `false` |

Связь «один ко многим»: `dialog.messages` содержит сообщения, а `message.dialog` возвращает диалог. При загрузке коллекции из базы сообщения упорядочены по `position`. При удалении диалога удаляются его сообщения; удаление отдельного сообщения сохраняет диалог. Удаление сообщения из ORM-коллекции `dialog.messages` также удаляет его запись. Пропуски в порядковых номерах после удаления допустимы.

Для реплик бота и оператора поля `intent` и `confidence` должны быть пустыми, а `is_fallback` — `false`; это проверяют схема запроса и ограничение БД. Бизнес-логика проверяет временные границы при создании и изменении сообщения, а также при изменении дат диалога.

Для добавления `messages` в базу с уже настроенными проектами, сценариями и диалогами достаточно повторно запустить `init_db.py`.

Таблица `backlog_items`:

| Поле | Назначение |
|---|---|
| `id` | Целочисленный первичный ключ, назначается автоматически |
| `project_id` | Обязательный внешний ключ на проект |
| `title` | Обязательный заголовок до 200 символов; пустые и пробельные заголовки запрещены |
| `description` | Подробности задачи; по умолчанию пустая строка |
| `priority` | Приоритет: `low`, `medium`, `high`; по умолчанию `medium` |
| `status` | Статус: `open`, `in_progress`, `done`; по умолчанию `open` |
| `source` | Источник: `requests`, `fallbacks`, `scenarios`, `manual`; по умолчанию `manual` |
| `created_at` | Дата и время с часовым поясом, назначаются базой автоматически |

Связь с проектом: `project.backlog_items` содержит задачи, а `backlog_item.project` возвращает проект. Задача без существующего проекта недопустима. При удалении проекта удаляются его задачи. При удалении отдельной задачи проект сохраняется. Удаление задачи из ORM-коллекции `project.backlog_items` также удаляет её запись.

Приоритет, статус и источник ограничены допустимыми значениями на уровне БД. Источник обозначает раздел, где обнаружили проблему; он не является ссылкой на конкретное сообщение или сценарий. Одинаковые заголовки задач разрешены. Для добавления `backlog_items` в существующую базу достаточно повторно запустить `init_db.py`.

### Обновление ранее созданной базы

Если таблица `scenarios` уже была создана до добавления диалогов, в ней нужно один раз добавить ограничение `scenarios_id_project_unique`. Выполните из папки `backend` перед запуском `init_db.py`:

```powershell
psql -h 127.0.0.1 -p 5432 -U postgres -W -d botinsight -v ON_ERROR_STOP=1 -f migrations/001_scenarios_project_key.sql
.\.venv\Scripts\python.exe init_db.py
```

Команда `psql` запросит пароль. Если она не найдена, используйте полный путь к `psql.exe` из папки `bin` установленного PostgreSQL. Обновление сохраняет записи. В новой базе ограничение создаётся автоматически из модели; повторно выполнять SQL-файл в базе, где ограничение уже есть, не нужно.

### Запуск backend

Из папки `backend` выполните:

```powershell
.\.venv\Scripts\python.exe -m uvicorn main:app --reload
```

Окружение `.venv` хранит зависимости отдельно от других Python-проектов. Команды используют Python из этого окружения напрямую, поэтому активировать его отдельно не требуется. При повторном запуске достаточно перейти в `backend` и выполнить последнюю команду.

### Проверка сервера

- Проверочный адрес: http://127.0.0.1:8000/ — ожидаемый ответ `{"message":"BotInsight API is running"}`.
- Проверка PostgreSQL: http://127.0.0.1:8000/health/db — HTTP `200` и `{"database":"ok"}` при успешном подключении. Если база недоступна или параметры подключения неверны, возвращается HTTP `503` и `{"detail":"Database is unavailable"}`. Текст ошибки не раскрывает пароль.
- Интерактивная документация API: http://127.0.0.1:8000/docs — позволяет отправлять запросы к серверу из браузера.
- Остановка сервера: `Ctrl+C` в терминале.

Параметр `--reload` автоматически перезапускает сервер при изменении кода во время разработки.

`config.py` читает `.env` из своей папки. `URL.create` формирует адрес подключения, в том числе для паролей со специальными символами. `database.py` создаёт Engine с проверкой соединений перед использованием и ограничением времени подключения до 5 секунд. Генераторная функция `get_db` выдаёт сессию на время обработки запроса и закрывает её при выходе из контекстного менеджера.

Общий обработчик ошибок валидации возвращает HTTP `422` и список `detail`. Каждый элемент содержит `loc` (расположение поля), `msg` (сообщение) и `type` (тип ошибки). Исходные значения не включаются в ответ: это позволяет корректно сообщать об ошибках даже для нечисловых и бесконечных значений вроде `NaN` и результата `1e309`.

### API проектов

Все адреса ниже относятся к backend, по умолчанию http://127.0.0.1:8000. Их можно проверить через `/docs`. Маршруты работают с PostgreSQL; frontend пока использует демонстрационные данные.

| Метод | Адрес | Действие | Успешный статус |
|---|---|---|---|
| `POST` | `/projects` | Создать проект | `201` |
| `GET` | `/projects` | Получить список проектов по возрастанию `id` | `200` |
| `GET` | `/projects/{project_id}` | Получить проект по идентификатору | `200` |
| `PUT` | `/projects/{project_id}` | Полностью обновить название и описание | `200` |
| `DELETE` | `/projects/{project_id}` | Удалить проект и связанные данные | `204`, без тела ответа |

Тело запроса для создания и обновления:

```json
{
  "name": "Support Bot",
  "description": "Бот поддержки клиентов"
}
```

Название обязательно, содержит от 1 до 100 символов и хотя бы один непробельный символ. Описание — строка, при пропуске используется пустая строка. Значения `null`, неверные типы и лишние поля запрещены. Идентификатор в адресе должен быть целым числом от 1 до 2147483647, что соответствует типу `Integer` в PostgreSQL. Одинаковые названия проектов разрешены.

`PUT` заменяет оба редактируемых поля: название обязательно; если не передать описание, сохранится пустая строка. Частичное обновление через `PATCH` пока не реализовано. `id` и `created_at` назначаются базой и не изменяются при обновлении.

Схема ответа `ProjectRead` содержит `id`, `name`, `description` и `created_at`. Дата передаётся строкой в формате ISO 8601 с часовым поясом. Список проектов возвращается JSON-массивом, а при отсутствии проектов — пустым массивом `[]`.

Ошибки:

- `404` и `{"detail":"Project not found"}` — проект с допустимым идентификатором не найден;
- `422` — запрос не соответствует схеме; ответ указывает поле и причину ошибки;
- `409` и `{"detail":"Data conflicts with database constraints"}` — нарушение ограничения целостности БД;
- `503` и `{"detail":"Database is unavailable"}` — ошибка подключения к БД. Технические детали и пароль не возвращаются клиенту.

Функции CRUD вызывают `commit()` для сохранения изменений и `refresh()` для получения актуальных полей созданного или обновлённого проекта. Если операция SQLAlchemy завершается исключением, зависимость `get_db` выполняет `rollback()` и повторно возбуждает исключение для обработчика ошибки.

| `DELETE` | `/projects/{project_id}/scenarios/{scenario_id}` | Удалить сценарий, сохранив диалоги | `204`, без тела ответа |

Тело запроса для создания и обновления:

```json
{
  "name": "Перевод денег",
  "description": "Помощь пользователю при переводе средств"
}
```

Схемы `ScenarioCreate` и `ScenarioUpdate` требуют название от 1 до 150 символов с хотя бы одним непробельным символом. Описание — строка, при пропуске используется пустая строка. `null`, неверные типы и лишние поля запрещены. `project_id` берётся из адреса; передавать или менять его через тело запроса нельзя. Идентификаторы в адресе имеют тот же допустимый диапазон, что и в API проектов.

`PUT` заменяет название и описание целиком, поэтому пропуск описания очищает его. Ответ `ScenarioRead` содержит `id`, `project_id`, `name` и `description`. Для существующего проекта без сценариев список равен `[]`.

Каждый маршрут проверяет существование проекта. Просмотр, изменение и удаление конкретного сценария дополнительно проверяют его принадлежность этому проекту. Сценарий другого проекта обрабатывается как отсутствующий. Это проверка связи данных; авторизация пользователя добавляется в лабораторной №4.

Ошибки:

- `404` и `{"detail":"Project not found"}` — проект не найден, включая запрос его списка сценариев;
- `404` и `{"detail":"Scenario not found"}` — сценарий отсутствует или принадлежит другому проекту;
- `409` и `{"detail":"Scenario name already exists in this project"}` — создание или переименование приводит к повтору названия в одном проекте;
- `422` — некорректное тело запроса или идентификатор;
- `503` — БД недоступна.

Уникальность названия проверяет PostgreSQL, в том числе при одновременных запросах. Одинаковые названия в разных проектах разрешены. При удалении сценария его диалоги и сообщения сохраняются: в диалогах очищается только `scenario_id`, а `project_id` остаётся прежним.

### API диалогов

| Метод | Адрес | Действие | Успешный статус |
|---|---|---|---|
| `POST` | `/projects/{project_id}/dialogs` | Создать диалог проекта | `201` |
| `GET` | `/projects/{project_id}/dialogs` | Получить диалоги проекта по возрастанию `id` | `200` |
| `GET` | `/projects/{project_id}/dialogs/{dialog_id}` | Получить диалог | `200` |
| `PUT` | `/projects/{project_id}/dialogs/{dialog_id}` | Полностью обновить редактируемые поля диалога | `200` |
| `DELETE` | `/projects/{project_id}/dialogs/{dialog_id}` | Удалить диалог и его сообщения | `204`, без тела ответа |

Пример тела запроса для создания и обновления:

```json
{
  "scenario_id": null,
  "external_id": "dialog-1",
  "started_at": "2026-10-26T12:00:00+03:00",
  "ended_at": "2026-10-26T12:05:00+03:00",
  "status": "completed"
}
```

`started_at` и `status` обязательны. Даты должны содержать часовой пояс; `ended_at` не может быть раньше `started_at`. Даты с разными смещениями сравниваются как моменты времени. Допустимые итоги: `completed`, `abandoned`, `fallback`, `operator`.

`scenario_id` — необязательное целое число из допустимого диапазона идентификаторов. Если сценарий указан, он должен существовать в проекте из адреса. `external_id` — необязательная строка до 255 символов, уникальная внутри проекта. В разных проектах одинаковые `external_id` разрешены, несколько диалогов без `external_id` также допустимы. Идентификатор и проект диалога нельзя задавать или менять через тело запроса.

`PUT` заменяет все пять редактируемых полей. Если `scenario_id`, `external_id` или `ended_at` пропущены, они становятся `null`. Ответ `DialogRead` содержит `id`, `project_id` и все пять редактируемых полей. Для существующего проекта без диалогов список равен `[]`.

Перед обновлением диалога `db.refresh(..., with_for_update=True)` перечитывает и блокирует его строку на время транзакции. Бизнес-логика получает самое раннее и самое позднее время сообщений через `MIN` и `MAX`. Новое начало не может быть позже первого сообщения, а указанное новое завершение — раньше последнего. Равенство допустимо. Если время завершения неизвестно (`null`), проверяется только нижняя граница. Создание, изменение и удаление сообщений также блокируют родительский диалог до завершения транзакции, чтобы согласовать операции с обновлением его дат.

Ошибки:

- `404` и `{"detail":"Project not found"}` — проект не найден;
- `404` и `{"detail":"Dialog not found"}` — диалог отсутствует или принадлежит другому проекту;
- `409` и `{"detail":"Dialog external_id already exists in this project"}` — повтор `external_id` внутри проекта;
- `422` со списком ошибок — поля запроса не соответствуют схеме;
- `422` и `{"detail":"Scenario does not exist in this project"}` — указан отсутствующий сценарий или сценарий другого проекта;
- `422` и `{"detail":"started_at must not be later than existing messages"}` — новое начало исключает сохранённые сообщения;
- `422` и `{"detail":"ended_at must not be earlier than existing messages"}` — новое завершение исключает сохранённые сообщения;
- `503` — БД недоступна.

Удаление диалога удаляет его сообщения, сохраняя проект и сценарий. Проверки бизнес-логики находятся в `services.py`; исключение `BusinessError` преобразуется в HTTP `422`.

### API сообщений

| Метод | Адрес | Действие | Успешный статус |
|---|---|---|---|
| `POST` | `/projects/{project_id}/dialogs/{dialog_id}/messages` | Создать сообщение | `201` |
| `GET` | `/projects/{project_id}/dialogs/{dialog_id}/messages` | Получить сообщения по возрастанию `position` | `200` |
| `GET` | `/projects/{project_id}/dialogs/{dialog_id}/messages/{message_id}` | Получить сообщение | `200` |
| `PUT` | `/projects/{project_id}/dialogs/{dialog_id}/messages/{message_id}` | Полностью обновить редактируемые поля сообщения | `200` |
| `DELETE` | `/projects/{project_id}/dialogs/{dialog_id}/messages/{message_id}` | Удалить сообщение | `204`, без тела ответа |

Пример тела запроса для создания и обновления:

```json
{
  "position": 1,
  "role": "user",
  "text": "Как отменить перевод?",
  "sent_at": "2026-10-26T12:02:00+03:00",
  "intent": "money_transfer",
  "confidence": 0.82,
  "is_fallback": false
}
```

Обязательны `position`, `role`, `text` и `sent_at`. Номер — целое число от 1 до 2147483647, уникальное в пределах диалога. Автор — `user`, `bot` или `operator`. Текст должен содержать хотя бы один непробельный символ. Время отправки должно содержать часовой пояс.

`intent` — необязательная строка до 150 символов; `confidence` — необязательное конечное число от 0 до 1; `is_fallback` — логическое значение, по умолчанию `false`. Для номера и логического признака используется строгая проверка типов: строки и логические значения не принимаются вместо номера, числа и строки не принимаются вместо логического значения. Для `confidence` допустимо JSON-число, включая целые 0 и 1, но не строка или логическое значение. Для сообщений бота и оператора `intent` и `confidence` должны быть `null`, а `is_fallback` — `false`.

`PUT` заменяет все семь редактируемых полей: пропущенные `intent` и `confidence` становятся `null`, а `is_fallback` — `false`. `id` и `dialog_id` доступны только в ответах. Перенос сообщения в другой диалог через тело запроса запрещён. Ответ `MessageRead` содержит все семь редактируемых полей, `id` и `dialog_id`. Для диалога без сообщений список равен `[]`. После удаления или изменения номера сообщения автоматическая перенумерация остальных реплик не выполняется.

Каждый маршрут проверяет проект, принадлежность диалога проекту и, для операций с конкретной репликой, принадлежность сообщения диалогу. При записи родительский диалог загружается с `SELECT FOR UPDATE` до поиска сообщения и проверки времени. Время сообщения не может быть раньше начала диалога или позже известного завершения; равенство допустимо. Если завершение неизвестно (`null`), верхняя граница не проверяется. Даты с разными часовыми поясами сравниваются как моменты времени.

Ошибки:

- `404` и `{"detail":"Project not found"}` — проект отсутствует;
- `404` и `{"detail":"Dialog not found"}` — диалог отсутствует или относится к другому проекту;
- `404` и `{"detail":"Message not found"}` — сообщение отсутствует или относится к другому диалогу;
- `409` и `{"detail":"Message position already exists in this dialog"}` — номер занят другой репликой этого диалога;
- `422` со списком ошибок — поля запроса не соответствуют схеме, в том числе правилам автора сообщения;
- `422` и `{"detail":"sent_at must not be earlier than dialog started_at"}` — сообщение раньше начала диалога;
- `422` и `{"detail":"sent_at must not be later than dialog ended_at"}` — сообщение позже завершения диалога;
- `503` — БД недоступна.

Удаление сообщения сохраняет его диалог, сценарий и проект. Удаление диалога удаляет его сообщения. Блокировка родительского диалога согласует запись сообщений с проверкой их границ при обновлении диалога, в том числе при одновременных HTTP-запросах.
